# ADR-0041: Comms Envelope, Per-Recipient Log, and the `next`/`ack`/`done` Verbs

**Status:** Accepted — captain word 2026-10-11 ("just finish and be sure the implementation and vision match your intent"; the build plan's §10 proposals adopted), relayed by the flywheel bot for factory task `23283d6f`.

**Decision in one sentence:** toron carries every comms message as one typed envelope appended once to a per-recipient log keyed by the L16 producer triple; delivery facts are written only by the tools the reader runs (`toron next`, `toron ack`, `toron done`), and those verbs are CLI-only behind `TORON_COMMS_INBOX`.

**Builds on:** [ADR-0040](0040-adopt-elm-effect-for-the-comms-kernel.md) (the kernel types come from `toron_core::kernel`; `ToronLog` implements `kernel::DurableLog`). [ADR-0037](0037-one-key-per-pin-project-scoped-visibility.md) (an envelope addresses an npub; `--as <name>` resolves through the W1 one-name-one-key roster).

**Does not change:** the frozen 41-tool / 25-resource MCP surface (ADR-0033: no tool is added); NIP-17 mail (`mail send`) and its stores; the doorbell and pane path (flywheel's, Phase 2/3).

## 2. Rules

1. **One triple, one row.** The same `(producer, epoch, seq)` with the same content returns the same offset and writes nothing. The same triple with different content is a hard conflict (`InboxError::PayloadConflict`; `NotAnEnvelope("payload conflict ...")` through the kernel entry, since the vendored `AppendError` is closed) and also writes nothing; a replay is never answered for content the log does not hold (2026-10-16, bd-envelope-conflict-3d7u). A lower epoch is fenced before dedupe (`StaleEpoch`), a seq gap is refused, a new epoch starts at seq 0. Producer epoch state never expires. `ToronLog` passes `kernel::durable_log_laws::all`.
   **Epoch claim (2026-10-16, bd-epoch-claim-z5m5).** A producer does not choose its epoch: `InboxStore::claim_epoch(producer, holder)` hands out the next one in a single `BEGIN IMMEDIATE` transaction (migration 0022, `inbox_epoch_claim`), strictly above every epoch the log has appended or claimed for that producer (the first is 0). Appends are fenced against the higher of the appended and the claimed epoch, so a claim fences every older incarnation before the claimant has appended anything; an epoch whose holder never appends is skipped. Callers that kept a local epoch lease (flywheel's file lock) switch to this. *The sender's own journal is such a caller (bd-journal-claim-epoch-4blu):* `outbox::send_and_recover` claims its journal epoch (producer `<npub>#journal`) instead of computing `producer_epoch + 1`, so concurrent runs of one sender never share a journal epoch, a run that journaled nothing still reserves its epoch, and a newer run fences an older run's journal. Consequence for callers: two runs of one sender racing each other can fence each other's journal appends (a refused append never landed, so a retry cannot duplicate); callers retry with jitter, or serialise runs of one sender.
   **Triple read (2026-10-16, bd-read-by-producer-seq-uozq).** `InboxStore::read_triple(msg, viewer)` and `toron inbox msg <producer:epoch:seq> --project P --as WHO` return the stored envelope for a triple, with its offset, recipient and a `fenced` flag (a newer epoch of the producer exists, appended or claimed), even after the epoch is fenced. It exists because a claimed epoch fences every older one, so a recovering sender cannot re-append an old triple to compare content: the append is refused as `StaleEpoch` before the payload is looked at. The read is one probe of the `UNIQUE (producer, epoch, seq)` index (a test pins the plan), is read-only, covers the inbox stream only (not the sender journal), and answers a stranger exactly as it answers an unknown triple: not found.
   **Wake decision (2026-10-16, bd-wake-core-rx1b).** `toron_core::wake::should_ring(&RingInput) -> RingDecision` is the redesign §4.1 rule as one pure function: unread mail (`head > cursor`), a verified binding at the current generation on a live pane, a ringable pane (`idle`/`done`; `working` only for urgent mail; `blocked`/`unknown` never), then either fresh mail (nothing outstanding: the cursor advanced since the last ring, so the count is 0, and the head is past the last ring) or the backoff elapsed, and a ring budget (`MAX_RINGS` 5, urgent `MAX_RINGS_URGENT` 3, backoff 30 s doubling to 15 min, urgent 5 s to 60 s). At the budget it answers `Escalate{wm}`, never a ring: that is P6. An unverified, stale or gone binding answers `Unbound` (re-verify, never ring). `rings_since_advance` resets only when the cursor advances. Known edge: a pane that stays `working`/`blocked` is neither rung nor declared deaf by this function; that stall belongs to the task lease. The Lean twin is `proto/Proto/Wake.lean` (P6 proved without `sorry`: a verified binding on a ringable pane with mail that is never read reaches `Escalate` within `2*maxRings+1` ticks, and no ring is ever issued past the budget); P4 (delivered needs cursor and recipient) is `Proto/Delivery.lean::delivered_needs_cursor_and_recipient`. `proto/vectors/wake.jsonl` (4536 vectors, from `lake exe proto wake-vectors`) is replayed against `should_ring` in `tests/proto_vectors.rs`. Departure from a literal reading of §4.1 ("new mail since the last ring"): mail that arrives after an *unanswered* ring waits for the backoff instead of ringing at once. A literal rule makes a flood of mail to a merely slow recipient spend the whole ring budget in moments and page the captain for it; the constant wake line already tells the recipient to run `toron next`, which reads up to the head at that time.
   **InboxProgram (2026-10-16, bd-inbox-program-qw18).** `toron_core::inbox_program::InboxProgram` is the recipient-side wake as one pure `Program` (it replaces the doorbell's `DoorbellModel` + `WakeModel` when flywheel's Phase 3 hosts it). Its serializable model holds, per recipient, the head, the cursor, the pane binding (`{pane_id, herdr_session, gen, verified, verified_by}`), herdr's last pane state and the ring bookkeeping; time arrives as `now_ms` on `Tick` (every recipient: the periodic full re-evaluation, so a lost hint costs nothing) and `Hint` (one recipient). Decisions come from `should_ring`. Commands: `Ring{pane_id, binding_gen, wm, line}` (the host types `wake_line(wm)` by pane id, never by name), `Reverify`, and on the ring budget the durable, keyed `RecordDeaf{recipient, wm, cause}` + `NotifySupervisor` + `NotifyCaptain`, once per watermark and cause. `rings_since_advance` resets only on a `Cursor` fact that moves the cursor forward; a ring is never taken as delivery. A binding that is unverified, stale or whose pane is gone is never typed into: it is re-verified each tick and, if that lasts the budget, escalates with cause `unbound`. `EventsLost` or `HerdrRestarted` bump the generation, which stales every binding at once. A deaf recipient is not rung again; a binding to a different pane (a restarted incarnation) gets a fresh budget, a re-verification of the same pane does not. A failed command (`CmdFailed`) changes nothing: the next tick decides again from durable state. Tests: unit scenarios, a 10k-hint flood through a tiny hint channel (no silent loss, the flood alone spends no budget), restart-from-snapshot equivalence at every offset, and properties over arbitrary histories (every ring is safe; every recipient reads or is declared deaf).
   **Task lookup (2026-10-16, bd-n24w).** `InboxStore::by_task(task_id, viewer)` and `toron inbox task <id> --project P --as WHO` list every envelope of a task the viewer sent or received, oldest first, with each delivery's live phase. It is read-only, reaches both tables by index (`inbox_delivery_by_task`, and `inbox_log_by_msg_key` from migration 0023; a test pins the plan), and answers a stranger exactly as it answers an unknown task id: an empty list.
   **Roles and authority at append (2026-10-16, Phase 4.1).** A role is a log fact: a `role@1` Control envelope `role{npub, role, context, gen}` (`toron_core::contracts::role_v1`), projected into `inbox_role` (migration 0024) in the same transaction as its append. `toron_core::authority` is the pure table `(role, class, contract) -> allowed?` from redesign §6.1 (`captain | supervisor | crew | peer | loop_self | verifier`; default-deny; `done` is the one non-envelope verb it names). `InboxStore::append_checked` (shared by `append_envelope` and the kernel `append_json` / `ToronLog` path) enforces it inside the append transaction, after the epoch fence and the replay answer and before any write: a violation is `Reject::Unauthorized { role, class, contract, expected }` and writes nothing, not even a sequence number. A context with no role fact is ungoverned and untouched; the first fact governs it, and from then on a sender with no role (and not the operator) is refused. The first fact of a context is `role{captain}` appended by the operator key (`InboxStore::with_operator`; the operator acts with captain authority everywhere). Issuing a role is itself ranked (`Authority::may_grant`): operator any; captain any but captain and never over a captain; supervisor the leaf roles over non-supervisors; nobody else. A role fact needs a `gen` above the one on record (`StaleGen`). A supervisor may not verdict a task it sent (read from the log: `Relation::OwnTask`); a verifier and a peer may not `done`. `verdict@1` lands only as the minimum a Control row needs (provisional body; it moves no task until Phase 4.3 wires it to the FSM); `steer`, `cancel`, `approval` are named in the table but are not contracts yet. Every role, grant and reject has a render test (`tests/comms_reject_render.rs`) and the CLI exits 3 with the typed refusal on stdout (`toron-cli/tests/comms_authority.rs`). Scope cut on purpose: the append path proves *who the envelope says it is from* (`from == --as` at the CLI, as before); there is no envelope signature check, so "operator-signed" means `from` is the operator's npub. API surface for flywheel: `docs/notes/2026-10-16-comms-roles-authority-api.md`. Live fixture transcript: `docs/notes/comms-roles-fixture/`.
2. **One table, many streams.** `inbox_log` backs every `ToronLog` stream (`inbox`, `journal`); the triple is unique across all of them. A sender loop's journal producer is `"{npub}#journal"`, so it can never collide with the envelope producer.
3. **Reads write delivery.** `toron next` commits the cursor advance and `Sent → Delivered` in one transaction; `--peek` commits neither. Only the recipient may read its stream (`not_recipient`); only the holder may finish (`not_holder`).
4. **The sender journals first.** The outbox appends its intent to its own journal before the provider runs. A crash between intent and append is recovered by reconciling (lookup by msg id), never by a blind retry; a crash after the append finds the row and settles without a second row.
5. **Folds are pure.** `Outbox`'s `Program` and the delivery FSM read no clock, env, filesystem, store or runtime (`tests/fold_purity.rs`, with a negative control on the interpreter). This test stands in for elm-effect-lints until that crate is wired.

## 3. Decisions (build plan §10, adopted)

- **Flag:** `TORON_COMMS_INBOX=1` (`1|true|on`). Off by default; every verb exits 2 with the flag's name while it is off. The `[comms] inbox_log` config key (2026-10-16, bd-652a) is the second switch, read by the CLI loader from the system, user and project config (a later layer that sets it wins; a layer that does not mention it leaves it alone). The env var overrides it whenever it is set and non-empty: `1|true|on` is on, `0|false|off` is off, and any other value is off, so a typo never opens the log. Neither set: on (amended 2026-10-17; previously off). Opt out with `0|false|off` or `inbox_log = false`. An unrecognised env value stays off. The decision is the pure `inbox::resolve_enabled(env, config)`. Deployment note: a toron binary older than this change rejects a config file that contains `[comms]` as invalid and ignores the whole file, so install the new binary before adding the key.
- **Default-on date:** flywheel `send --via-inbox` is per-recipient opt-in from the Phase 2 merge, default-on **2026-10-25**, and the legacy payload-typing path is deleted no later than **2026-11-08** (spec §12's hard date).
- **CLI-only verbs.** `next`/`ack`/`done`/`inbox append` are CLI nouns that open the shared durable root directly (the `ack-sla` / `reserve yield` pattern). No MCP tool; an additive tool needs its own ADR-0033 record.
- **Wake fold location:** Phase 3 hosts it in the flywheel doorbell; the long-term home (`toron serve` vs doorbell) is decided at Phase 7.
- **beads scope:** `task@1.scope_paths` carries the bead's paths; the bead id rides in `task@1.bead`.
- **`T_orphan` = max(2 × lead lease TTL, 10 min)** (recorded in ADR-0037's log; used in Phase 4b).
- **Comms feature freeze:** no new doorbell/wake/send features outside the build plan until 4b lands (recorded in the build plan and briefs only).

## 4. Deviations from the build plan, on purpose

- `ToronJournal: kernel::JournalStore` moves to Phase 2: the Phase 1 sender journals intents through a `ToronLog` stream (`journal`), which is what the Loop's `DurableLog` needs; the effect-record journal arrives with flywheel's `mail.append` effect.
- The reader-side `InboxProgram` (cursor + wake + binding state) is Phase 3 work, where it replaces `DoorbellModel` + `WakeModel`. Phase 1's cursor lives in the store and is advanced by `next`.
- Lean vectors are exhaustive over a small domain (2160 delivery steps, 125 log traces) instead of `--seed N --count 10000` random draws: every (phase, class, event) case is covered, and `--check` fails if the committed copy drifts. Envelope validation is tested in Rust only (`Proto/Envelope.lean` deferred).
